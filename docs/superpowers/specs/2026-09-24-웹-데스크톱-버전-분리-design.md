# 설계: 손글씨 인식 프로그램의 웹·데스크톱 버전 분리

> 이 문서는 Superpowers의 brainstorming → 설계 문서 형식을 따릅니다.
> 이 작업을 한 클라우드 세션에는 Superpowers 플러그인이 설치되어 있지 않아, 같은 형식으로 Claude가 직접 작성했습니다.

## 1. 요구사항

- 손글씨 인식 프로그램을 **웹 버전**과 **데스크톱 버전**으로 나누어 개발한다.
- 웹 버전은 **외부 라이브러리 없이 순수 자바스크립트로 추론**하고, **GitHub Pages에 정적으로** 올릴 수 있어야 한다.
- `web_version/`은 새로 작성하고, `desktop_version/`은 기존 코드를 옮긴다 (`git mv`로 이력 유지).
- 각 폴더와 루트에 `CLAUDE.md`를 둔다.
- 페이지 맨 위에 "학번 2601953 이름 안서연"이 보여야 한다 (과제 요구사항).

## 2. 현재 상태 (분리 전)

- 루트에 `model.py`, `train.py`, `app.py`, `make_shortcut.py`, `mnist_cnn.pt`, `app_icon.ico`가 있었다. 환경은 Windows + Python 3.13 + PyTorch CPU.
- 전처리는 별도 파일이 아니라 `app.py`의 `전처리()`에 있다 (노트의 `preprocess.py`에 해당).
- 이전 웹 페이지는 onnxruntime-web(CDN)으로 `mnist_cnn.onnx`를 읽었다 → "외부 라이브러리 없이" 조건에 맞지 않아 다시 만든다.
- 모델 `숫자인식CNN`: 합성곱 4개(각각 배치정규화 + ReLU), 최대풀링 2개, 드롭아웃, 전결합 2개. `state_dict`에는 배치정규화 통계까지 텐서 32개가 있지만, 웹으로 보낼 텐서는 배치정규화를 합성곱에 합친 **12개**(합성곱 4 + 전결합 2의 weight/bias, 약 3.5MB)다.

## 3. 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 파이썬 파일 | `model.py`, `train.py`, `app.py`, `make_shortcut.py`는 옮기기만 하고 내용은 거의 그대로 | 동작 중인 데스크톱 앱을 깨지 않기 위해. 단, `train.py`는 폴더 이동 후에도 같은 폴더에 저장하도록 `__file__` 기준 경로로 바꿈 |
| 가중치 형식 | `가중치.bin`(float32 리틀 엔디언, 헤더 없음) + `가중치정보.json`(층 순서·형상·오프셋·정규화 상수) | 순수 JS로 `Float32Array`에 복사 없이 올릴 수 있음. 형상과 상수를 JS에 하드코딩하지 않음 |
| 배치정규화 | 내보낼 때 합성곱에 합침 | 웹에서 계산할 층 종류가 줄고(합성곱·ReLU·최대풀링·전결합), 결과는 같음 |
| 정규화 상수 | `app.py`에서 읽어 `가중치정보.json`에 기록 | 이미 `train.py`/`app.py` 두 곳에 중복된 상수가 웹 쪽으로 번지지 않게 |
| 전처리 축소 | PIL `LANCZOS` 리샘플링을 JS로 그대로 구현 | 브라우저 `drawImage` 축소는 PIL과 결과가 달라 파이썬과 같은 입력을 보장할 수 없음. 면적 평균 같은 근사 대신 처음부터 같은 계산을 택함 |
| 반올림 | 파이썬 `round()`(짝수 반올림) 구현 | 새 크기·무게중심 이동량이 정확히 .5일 때 JS `Math.round`와 달라짐 |
| 파일 구성 | `그림판.js` / `전처리.js` / `모델.js` / `앱.js` + `index.html` + `스타일.css` | 역할별로 나눠 각각 따로 검증 가능. `전처리.js`, `모델.js`는 Node.js에서도 `require` 가능 |
| 배포 | `main` 루트를 GitHub Pages로 배포하고, 루트 `index.html`이 `web_version/`으로 이동 | 기존 Pages 설정(브랜치 루트)을 바꾸지 않고 주소를 그대로 유지 |
| 검증 | `검증데이터만들기.py`가 파이썬 결과를 저장하고 `검증.html`이 대조 | 파이썬과 JS가 같은 그림에서 같은 전처리·점수를 내는지 숫자로 확인 |

## 5. 데이터 흐름

```
[데스크톱] train.py → mnist_cnn.pt → 가중치내보내기.py → 가중치.bin + 가중치정보.json
[웹]      그림판.js(280x280 흑백) → 전처리.js(28x28 정규화) → 모델.js(점수 10개) → 앱.js(소프트맥스, 표시)
[검증]    검증데이터만들기.py(app.py 전처리 + PyTorch 결과) → 검증.html(JS 결과와 대조)
```

## 6. 위험과 대응

- **전처리 불일치** → PIL 알고리즘 그대로 구현 + 검증 페이지로 전처리 결과 자체를 비교 (차이 1e-4 미만).
- **가중치 파일 손상·불일치** → `모델.js`가 바이트 길이(4의 배수)와 형상·오프셋 범위를 미리 검사해 알아보기 쉬운 오류를 냄.
- **`file://`로 열기** → `fetch`가 막혀 모델을 못 읽음. 화면에 로컬 서버 사용법을 안내.
- **검증 표본 편향** → MNIST 10배 확대만 쓰면 크기가 늘 10의 배수라 쉬운 경우만 시험함. 크기·위치를 바꾼 MNIST와 `app.py` 방식으로 획을 그린 표본을 섞음.

## 7. 검증 기준

- 파이썬과 JS의 전처리 결과 차이 < 1e-4, 예측 100% 일치.
- 브라우저에서 0~9를 직접 그려 모두 인식, 외부 네트워크 요청 0건.
- 배포 주소에서 학번·이름 표시와 인식 동작 확인.

## 8. 브레인스토밍 질문과 결정 (2026-09-24 20:14 추가)

Superpowers brainstorming 스킬이 던지는 질문 형식(대안, 선택, 근거, 감수하는 비용)으로 정리했다. 결정 1~5는 원래 프롬프트에서도 나오는 질문이고, 6~8은 "외부 라이브러리 없이 순수 자바스크립트로 추론하고, GitHub Pages에 정적으로 올릴 수 있어야 해"가 추가되면서 새로 생기는 질문이다.

### 결정 1 — 웹 버전의 추론을 어디서 할 것인가
| 대안 | 장점 | 단점 |
|---|---|---|
| **브라우저 단독 ✅** | 서버 불필요, 정적 호스팅 가능, 그림이 기기 밖으로 안 나감 | 전처리를 JS로 다시 구현해야 함 |
| 파이썬 서버 | `app.py`의 `전처리()` 재사용 | 브라우저만으로 못 씀, 배포에 파이썬 환경 필요 |

- 선택 근거: 프롬프트가 "순수 자바스크립트로 추론"을 요구한다.
- 감수하는 비용: 가장 깨지기 쉬운 전처리를 손으로 옮겨야 한다. 그래서 `검증.html`로 파이썬과 대조하는 장치를 함께 만들었다.

### 결정 2 — 학습, 데이터, 변환 스크립트의 위치
| 대안 | 장점 | 단점 |
|---|---|---|
| **desktop이 원본, web은 산출물만 ✅** | `web_version`에 파이썬 의존성 0, 폴더째 떼어 낼 수 있음 | 가중치를 바꾸면 내보내기를 다시 돌려야 함 |
| 루트에 공통 폴더 | 중복 없음 | 폴더가 셋, `web_version` 단독 분리 불가 |
| web에 변환 스크립트 | 의도가 드러남 | 폴더 간 경로 의존 발생 |

- 감수하는 비용: 수동 동기화 지점(`가중치내보내기.py` 재실행)이 생긴다. `web_version/CLAUDE.md`에 적었다.

### 결정 3 — GitHub Pages 배포를 범위에 넣을 것인가
Pages의 "Deploy from a branch"는 소스 폴더로 루트나 `/docs`만 고를 수 있어 `web_version/`을 직접 지정할 수 없다.

| 대안 | 장점 | 단점 |
|---|---|---|
| Actions 워크플로 | 폴더 이름 자유, 웹 파일만 게시 | 워크플로 파일 추가, 저장소 설정(Pages 소스)을 바꿔야 함 |
| **Pages 소스를 루트로 ✅** | 설정이 가장 간단, 이미 배포 중인 설정 그대로 | 주소가 `.../web_version/`으로 이동, 저장소 전체가 게시됨 |
| 저장소 둘로 분리 | 기본 설정만으로 끝 | 산출물이 저장소 경계를 넘음 |

- 선택 근거: 과제 제출 주소(`https://dkstjdus123.github.io/Study01_MNIST/`)가 이미 루트 배포로 동작하고 있었다. 설정을 바꾸다 배포가 깨질 위험을 피하고, 루트 `index.html`이 `web_version/`으로 이동시켜 주소를 그대로 유지했다.
- 감수하는 비용: `desktop_version`, `docs`도 Pages로 게시된다. MNIST 원본(`data/`)은 `.gitignore`로 빠져 있어 올라가지 않는다.

### 결정 4 — 웹 버전의 기능 범위
- **데스크톱과 동등 + 터치 입력 ✅**: 그리기, 지우기, 붓을 떼면 인식, 예측, 신뢰도, 0~9 확률 막대. 포인터 이벤트로 마우스, 터치, 펜을 한 코드로 처리하고 `touch-action: none`으로 그릴 때 화면이 스크롤되지 않게 했다. 두 번째 손가락과 오른쪽 버튼은 무시한다.
- 대안 "28x28 전처리 미리보기"는 데스크톱에 없는 기능이라 두 버전 비교를 흐린다. 그 역할은 `검증.html`이 맡는다.

### 결정 5 — 브라우저 추론을 무엇으로 구현할 것인가
| 대안 | 장점 | 단점 |
|---|---|---|
| ONNX 변환 + ONNX Runtime Web | 모델 구조를 옮겨 적을 필요 없음 | 외부 라이브러리(CDN) 필요 → 프롬프트 조건 위반 |
| **가중치 직접 내보내기 + JS 순전파 ✅** | 외부 라이브러리 0개, 폴더째 정적 호스팅 | `model.py`를 바꾸면 `모델.js`도 고쳐야 함 |

- 경위: 이전 웹 페이지는 ONNX Runtime Web(CDN)을 썼다. 새 프롬프트의 "외부 라이브러리 없이" 조건 때문에 ONNX 관련 파일(`export_onnx.py`, `mnist_cnn.onnx`)을 지우고 직접 구현으로 바꿨다. 모델은 합성곱 4개라 순전파가 한 장에 약 50ms로 충분히 빠르다.

### 결정 6 — "외부 라이브러리 없이"의 범위
- **실행할 때 쓰는 라이브러리, CDN, 빌드 도구(npm 등) 모두 없음 ✅.** 브라우저가 기본으로 주는 기능(Canvas, fetch, Float32Array)만 쓴다.
- 개발 중 검증에는 파이썬(PyTorch, Pillow)과 Node.js를 썼다. 이들은 저장소의 웹 페이지 실행에 필요하지 않다.

### 결정 7 — 정확성 검증 방법
| 대안 | 판정 |
|---|---|
| 손으로 그려 보기만 | 틀려도 원인을 모름, 재현 불가 → 보조 수단으로만 |
| **파이썬 결과와 대조하는 검증 페이지 ✅** | 같은 그림을 두 경로로 처리해 전처리 결과와 점수를 숫자로 비교 |

- `검증데이터만들기.py`(파이썬 결과 저장) + `검증.html`(JS 결과와 대조). 표본은 MNIST 10배 확대 50장, 크기와 위치를 바꾼 MNIST 150장, `app.py` 방식으로 그린 획 30장.
- 기준: 전처리 차이 1e-4 미만, 예측 100% 일치. 마지막으로 브라우저에서 0~9를 5가지 형태로 50번 그려 확인했다 (50/50).

### 결정 8 — 가중치 파일 형식
| 대안 | 장점 | 단점 |
|---|---|---|
| JSON 하나 | 파일 하나 | 숫자 87만 개를 글자로 적어 크기가 몇 배, 파싱이 느림 |
| **바이너리 + JSON 정보 파일 ✅** | `Float32Array`로 복사 없이 읽음, 약 3.5MB | 파일이 둘 |

- `가중치.bin`: float32 리틀 엔디언, 헤더 없음. `가중치정보.json`: 층 순서, 형상, 오프셋, 정규화 상수.
